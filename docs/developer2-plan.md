The owner can manipulate its own tables without object grants to itself. Ordinary indexes on its own tables do not require a blanket `CREATE ANY INDEX` grant. CREATE SEQUENCE and CREATE PROCEDURE are already granted for future own-schema sequences and PL/SQL procedures/packages; their presence does not require using these objects. For runtime separation, propose optional login users `D2_VALIDATION_APP`, `D2_RISK_APP`, and `D2_CONFIGURATION_APP`. They add no separately owned application tables. Each needs `CREATE SESSION` and specific object privileges on its corresponding owner's objects, not table-creation or migration privileges:

| Runtime identity | Proposed object privileges | Qualification |
|---|---|---|
| `D2_VALIDATION_APP` | `SELECT`, `INSERT` on validation results/checks; narrowly scoped `UPDATE` if mutable attempt/outcome fields are approved | No `DELETE` by default. Finalized check evidence should remain immutable; settle insert-only versus pending-to-final updates at M1. |
| `D2_RISK_APP` | `SELECT`, `INSERT` on assessments, factors, snapshots; narrowly scoped `UPDATE` only if an approved pending-to-final model requires it | No `DELETE` by default. Finalized assessment evidence must not be overwritten. |
| `D2_CONFIGURATION_APP` | `SELECT`, `INSERT` on configuration tables; scoped `UPDATE` for editable draft fields and activation/effective state | No `DELETE` by default. Retain historical versions. Table-level UPDATE alone cannot distinguish draft from active rows; enforce lifecycle rules through the service and, if required, a reviewed database access design. |

If explicit sequences are used, the corresponding runtime user needs `SELECT` on those named sequences to obtain generated values. Identity-based IDs should be reviewed separately. Grant no runtime user access to another service's schema or teammate-owned data. The schema-qualified mapping/default-schema choice remains an implementation decision.

Using the owner as the runtime login is a simpler prototype option but retains the owner's inherent DDL and broad object control; revoking CREATE TABLE does not make existing owned objects read-only. Separate runtime identities are therefore recommended when enforcing privilege separation. Neither option is yet approved.

Application identities do not need SYSTEM credentials, `DBA`, `RESOURCE`, `CREATE USER`, `ANY` privileges, `UNLIMITED TABLESPACE`, or privileges on system/dictionary objects. Provisioning of the three owner accounts and their recorded grants/quotas is complete according to the user. Any future runtime-account provisioning is a separate action. Administrative account privileges are not inherited by applications.

Privilege references: Oracle's [CREATE TABLE prerequisites](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/CREATE-TABLE.html) specify CREATE TABLE for own-schema creation and storage quota; its [privilege and role guide](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbseg/configuring-privilege-and-role-authorization.html) distinguishes system/object privileges and local PDB grants. Runtime permissions above are proposed from the planned service operations, not an Oracle-mandated application role.

### M2a implemented contract and evidence

Implementation: [business-configuration-service](../business-configuration-service/README.md), Java 21 / Spring Boot 4.1.1 / installed Maven 3.9.16. Endpoint: GET /api/v1/configuration/versions, port 8086. Approved prototype access policy: FINANCE_MANAGER only, represented without ROLE_ in JWT roles. This policy comes from the user's implementation instruction, not the business scope document.

The minimal JSON DTO contains versionId (string), versionNumber (integer), versionLabel (string), publicationState (DRAFT/PUBLISHED string), isDemonstration (boolean), createdAt (ISO-8601 UTC string with Z), and publishedAt (same timestamp format or null). Reads are ordered by VERSION_NUMBER ASC, VERSION_ID ASC. No rows returns HTTP 200 with []; unavailable data does not silently return an empty list.

JWT signature and expiry are verified. exp is mandatory and future; subject is mandatory/nonblank; userId must be positive, integral and fit Java Long, supplied as a number or digit string. Invalid/missing authentication returns 401; authenticated users without unprefixed FINANCE_MANAGER return 403. Local/generated accounts, Basic/form login and sessions are disabled. Issuer/audience alignment with Developer 1 remains pending; no values were invented or enforced. External signing configuration uses the existing verifier's raw UTF-8 HMAC encoding.

Authentication fixes: Bearer scheme matching is case-insensitive (Bearer/bearer/BEARER), while the token itself is passed unchanged to strict verification. Every 401 includes a WWW-Authenticate Bearer challenge with realm business-configuration-service. Missing/empty Bearer credentials and unsupported schemes receive a challenge without an OAuth token error; invalid/expired tokens receive error="invalid_token". JSON errors remain sanitized and manager-only/403 behavior is preserved. No token or exception details are reflected in the challenge.

Credentials use CONFIG_DB_USERNAME and CONFIG_DB_PASSWORD environment configuration; signing uses CONFIG_JWT_SECRET. No real credentials/key are stored in the service or plan. The approved database target is localhost:1521/FREEPDB1 and account D2_CONFIGURATION. M2a reads the seven DTO fields; M2b adds a parameterized draft INSERT, allocation read and identity readback only. SQL initialization, DDL generation and migrations remain disabled; no JPA/migration tooling, business seeds or mock fallback is included. ## M2b request, concurrency and evaluation flow

Approved slice: POST /api/v1/configuration/versions on port 8086, FINANCE_MANAGER only as a prototype policy. Request fields: required nonblank versionLabel (100 characters maximum); optional/null description (1000 maximum); required JSON boolean isDemonstration; exact scorePolicyCode SUM or CAP_AT_MAX; maxFinalScore absent/null for SUM or a positive JSON integer for CAP_AT_MAX. The implementation bounds the score to 2147483647 to match the reviewed table constraint. Lengths count Unicode code points, values are stored as supplied, and unknown fields are rejected. Malformed/invalid requests return sanitized 400 / INVALID_REQUEST before database access.

The JWT filter verifies authentication, then the security chain enforces the role. The controller validates the body and takes createdByUserId from JwtPrincipal. The transactional service reads the highest versionNumber across all versions and attempts MAX+1. Oracle's existing reviewed UK_CFG_VERSION_NUMBER constraint arbitrates concurrent attempts, including an empty table: no silent overwrite or duplicate committed version is permitted. After the M2b review fix, only an INSERT executeUpdate failure with Oracle vendor code 1 and the exact qualified D2_CONFIGURATION.UK_CFG_VERSION_NUMBER identity returns sanitized 409 / VERSION_ALLOCATION_CONFLICT, with rollback and no automatic retry. The classifier follows SQLException cause/next chains and strictly parses the first qualified identity in the ORA-00001 diagnostic; unknown or ambiguous identities fail closed. Primary-key collisions, other constraints, number exhaustion and generated-key/readback failures return sanitized 503 without allocation retry advice. No diagnostics are exposed. The deployed unique constraint, live diagnostic format and real simultaneous writes remain unverified; this strategy depends on that constraint. POST has no idempotency key, so retrying after an uncertain/lost response may create an additional draft.

The repository binds a single INSERT in CONFIGURATION_VERSIONS, omitting VERSION_ID for Oracle identity, setting DRAFT, recording the JWT actor and a UTC timestamp at microsecond precision. Publication metadata and content hash are omitted/null; ROW_VERSION retains its existing default. No rules/bands/thresholds/SLA/current-pointer rows are inserted. JDBC requests VERSION_ID by name, checks exact positive Java Long conversion, and reads the row back within the transaction. Commit completes before HTTP 201 with the existing seven-field DTO, string ID and UTC timestamps; subsequent GET reads the committed row in deterministic order. Other database/transaction failures remain sanitized 503; unexpected failures remain sanitized 500.
