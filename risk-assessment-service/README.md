## Evidence adapter contract

`EvidenceAdapter` is an integration port only. Adapters must provide same-supplier INR evidence, an exact common UTC cutoff, stable source snapshot IDs, sufficient coverage and an explicit COMPLETE/UNAVAILABLE/INCOMPLETE status. COMPLETE is an authoritative completeness guarantee, including pagination and as-of status, not merely a successful API response. Payment windows are `[cutoff-windowSeconds, cutoff)`; amount baselines use completedAt, activity/near-duplicate histories use submittedAt. Supplier creation/reactivation age windows include both endpoints. New-supplier evaluation needs exactly one supplier snapshot; reactivation also needs actual status transitions. PriorAssessment represents a completed assessment's original triggered factors; overrides do not erase that original evidence.

For unavailable dependencies, `Evidence.unavailable(supplierId, currencyCode, cutoff)` records the requested scope without inventing a source snapshot or coverage. Those metadata fields are mandatory for COMPLETE evidence; unavailable/incomplete evidence always fails enabled dependent rules.

The engine excludes supplied current/retry submission identities before evaluating history and deduplicates identical historical rows by logical submission identity. Conflicting rows fail closed. Previous flags count distinct submissions, and PREVIOUS_RISK_FLAGS cannot qualify itself. No assessment-once enforcement is claimed. Adapters must agree submission/resubmission identity, canonicalize retry records, certify historical validation and resolve Developer 1 LocalDateTime values to the agreed timezone. Current requester-scoped payment APIs cannot supply authoritative history across requesters. Payment/invoice DTOs lack currency; previous factor history and validation handoff APIs are not available. No endpoint is assumed to exist.

## Atomic acceptance and lookup contract

Import `RiskPersistenceConfiguration` explicitly into a host Spring context; this jar has no startup entry point. Supply `RISK_DB_USERNAME` (D2_RISK) and `RISK_DB_PASSWORD` externally, plus optional `RISK_DB_URL` (default localhost:1521/FREEPDB1). Never commit local values. There is no connection-initialization SQL, DDL, migration or seed code. The supplied application resource disables SQL initialization, Hibernate DDL, Flyway and Liquibase; a future host must preserve those settings. No live Oracle acceptance test is run by the reactor command above.

`RiskAcceptanceService.accept(AcceptanceRequest)` accepts an explicit namespaced `(source,key)`, separate payment/requester IDs, validation reference/revision, validated current `Payment`, cutoff, immutable current/retry exclusion set, evaluator build identifier, optional `RiskConfiguration` and optional correlation ID. Schema supplier/invoice IDs must be positive Java Long decimal strings; opaque engine submission/evidence IDs remain separate frozen facts. No assumption equates an engine submission ID, payment ID or correlation ID with the namespaced logical key. Developer 1 must confirm their adapter mapping and genuine resubmission lineage.

A new logical key requires supplied configuration; there is no active/newest-version lookup. The first committed transaction freezes all accepted facts, exclusions, cutoff, evaluator and supplied configuration. Every retry must supply the same facts. A null configuration explicitly reuses the saved snapshot; an explicit configuration must have identical canonical identity, contents and source provenance. Changing cutoff, validation revision, exclusions or facts conflicts. Correlation IDs are excluded from comparison and the first value is retained. Existing assessments are reused in any work state; ACCEPTED does not mean scored or low risk. Lookup returns string IDs/rowVersion, immutable canonical payloads and local hashes. No evidence/history is fetched or frozen yet, and INPUT_HASH stays null.

`risk-canonical-v1` hashes UTF-8 canonical JSON with SHA-256, sorted object keys/declared sets, rules in evaluation order and bands by minimum. IDs are normalized decimal strings, money uses exact scale-two strings, ratios normalized exact decimal strings, timestamps UTC ISO-8601 with nanoseconds retained and absent optional fields explicit null. There is no floating-point conversion. `risk-engine-v1` identifies the snapshot shape. Acceptance and configuration digests are distinct; neither caller-supplied hash nor opaque `contentHash` is trusted as a local digest. Retain these format implementations for retries across future upgrades.

The service owns a REQUIRES_NEW, READ_COMMITTED transaction: lookup, insert assessment with Oracle-generated identity, insert immutable snapshot, associate it, verify readback and commit. Initial rowVersion stays zero; the association belongs to initial creation. Only the parent INSERT's recognized `D2_RISK.UK_RSK_SUBMISSION` collision rolls back and starts a fresh lookup transaction for the concurrent winner. Matching data reuses it; conflicting data raises sanitized `SUBMISSION_CONFLICT`. Unknown/primary-key constraints, missing snapshots and invalid readback raise sanitized `RISK_PERSISTENCE_UNAVAILABLE`. A commit/network ambiguity requires another idempotent call using the same identity, never blind recreation. Repository writes require an active writable transaction bound to their datasource.

Offline transaction tests use a real Spring JDBC transaction manager with mocked connections/statements; they are distinct from live Oracle verification. Durable historical as-of visibility, identity/retry mapping and coherent published-configuration sourcing are still integration dependencies. Complete scoring, factor sets and callbacks remain later milestones.

## Scoring finalization library contract

`RiskFinalizationService.finalizeAssessment(FinalizationRequest)` takes the namespaced identity, current post-freeze/renewal `WorkLease`, and expected acceptance/configuration/input hashes. Hashes are preconditions: persisted configuration, acceptance and the complete frozen graph are independently reconstructed and verified locally. No supplied score, factor or replacement input is accepted. The pinned executable registry currently supports **`risk-scoring-v1`** only; accept this evaluator identity for new work. Unknown historical identities fail closed with `EVALUATOR_UNAVAILABLE`; they are never silently aliased to the current engine. Retain executable versions and canonical decoders for historical work.

Execution has three phases: a short Oracle `SET TRANSACTION READ ONLY` snapshot; pure evaluation with any caller transaction suspended and no database lock; then a REQUIRES_NEW writable transaction locking the parent and verifying the frozen identity/graph plus the full lease again. Seven unique factors are validated against configured weights/enabled flags, exact raw total, configured cap and configured band. They retain original outcomes (including valid zero-contribution INSUFFICIENT_HISTORY), matched IDs, observations and explanations. Each enabled factor points to the manifest; its `risk-factor-v1` CLOB includes the full frozen evidence reference graph. Disabled factors have null primary evidence and no references. Upstream rule-row IDs are absent from the engine snapshot and remain null rather than invented.

All seven inserts, final score/band/timestamps, factor count, rowVersion increment and lease clearing commit together. Oracle remains the clock authority: the final conditional UPDATE checks token/epoch/attempt/rowVersion/exact expiry and `SYSTIMESTAMP` after factor inserts; readback also rechecks the original expiry before returning for commit. If evaluation succeeds but authority expires before the final guarded write or during readback, finalization rejects and rolls back all factors/completion. It does not extend or revive the lease. A newly claimed worker may evaluate the unchanged frozen input. Technical/unresolved-policy outcomes create no completion or final factors; failure/blocked recording remains the separate existing fenced work operation.

A completed retry uses the original successful lease capability and the same frozen hash preconditions. A versioned one-way fence digest in every factor CLOB verifies that capability after the parent clears its lease token. The token itself is not stored in factor details. Matching retries return verified stored factors/scores/timestamps, even after lease expiry or without an evaluator artifact, without rescoring or updating completion time. Superseded capabilities reject. Concurrent finalizers may evaluate independently; the parent lock permits only one atomic factor set. User-run Oracle verification is recorded below. No HTTP operation, scheduler or callback is supplied.

## Work claiming and fencing contract

`RiskEvidenceService.freeze(EvidenceFreezeRequest)` accepts a current `WorkLease`, the explicit original `AcceptanceRequest` with typed configuration, a supplied immutable `RiskInput`, and four `Kind -> Source(service, recordReference, revision)` dependency provenance entries. No adapter endpoint or external call is assumed. Configuration/acceptance hashes are recomputed against the saved snapshot; current facts, cutoff, exclusions, INR, supplier scope, record consistency and coverage for every enabled rule must match. Historical payments/prior assessments must already exclude current/retry identities. Prior assessedAt remains the adapter's original COMPLETED_AT contract. COMPLETE includes an upstream completeness/as-of guarantee; this operation cannot independently verify pagination or historical visibility.

Partial capture is **all-or-nothing**: required UNAVAILABLE/INCOMPLETE/short coverage rejects with EVIDENCE_NOT_READY and no input writes. COMPLETE empty history stays distinct from missing evidence and may later yield insufficient history. Disabled dependencies may retain explicit unavailable/incomplete envelopes, records and provenance; they are never relabelled COMPLETE. The manifest is usable for the frozen enabled-rule set, not a claim that every disabled source is available. No attempt diagnostic is inserted by freezing; callers may separately record failure through the existing fenced work operation. Unexpected orphan partial input rows are refused without overwrite.

A successful freeze appends five INPUT rows (CURRENT_INPUT, PAYMENT_HISTORY, SUPPLIER, SUPPLIER_TRANSITIONS, PRIOR_ASSESSMENTS), all attempt 0, and one MANIFEST/ENGINE_INPUT row referencing their IDs/hashes and the full canonical input. `risk-evidence-canonical-v1` uses exact scale-two money strings, UTC nanoseconds, explicit nulls, sorted object keys/declared sets, and preserved record-array order. It locally computes evidence and assembled input hashes; the manifest hash also includes physical references and is distinct from INPUT_HASH. Input/manifest shapes are versioned separately. Temporary CLOB locators avoid stream binding with Oracle generated-key RETURNING.

The parent lock, child inserts, manifest association, INPUT_HASH/INPUT_FROZEN_AT, rowVersion increment and readback are one REQUIRES_NEW transaction. Oracle is the lease clock authority and the final SQL checks token/epoch/attempt/rowVersion/exact expiry plus SYSTIMESTAMP. The returned `FrozenInput.lease` contains the refreshed rowVersion. The returned `FrozenInput.input` is reconstructed from the verified persisted manifest using a version-gated exact decoder (BigDecimal money strings, Instant nanoseconds, strict booleans/enums/sets) and compared with supplied input; it does not echo the caller's object. Identical evidence under a current fence verifies/reuses all existing rows/hash/time without advancing rowVersion; a final guarded no-op parent update checks expiry even on reuse. Differing input/provenance conflicts; stale fences reject. Failure, expiry and takeover leave frozen data intact. There are no scores, final factors, lifecycle completion, callbacks, HTTP endpoints or schema changes. The user-run evidence suite verified freeze bindings/association, actual rollback and populated frozen-input recovery; live COMPLETED-state behavior remains unverified.

The imported context now requires an explicit positive ISO-8601 `RISK_LEASE_DURATION` (for example `PT30S` is a technical demonstration setting, not an approval SLA). It has no scheduler or HTTP operation. `RiskWorkService.claim(assessmentId, expectedRowVersion)` locks an accepted parent and permits ACCEPTED, RETRYABLE_FAILURE, or IN_PROGRESS with expiry **at or before** Oracle's current time. BLOCKED requires explicit intervention; this milestone supplies no unblock operation. COMPLETED cannot be claimed, renewed or failed. An expired attempt can be superseded without modifying its frozen acceptance/configuration/input or any earlier diagnostic.

Claims and takeovers generate a new opaque token and increment epoch, attempt and rowVersion. The returned `WorkLease` carries string assessmentId/rowVersion, exact Java Long epoch, int attempt and UTC nanosecond expiry. `renew(lease)` preserves token/epoch/attempt, increments rowVersion and returns the refreshed fence. `fail(lease, WorkDiagnostic)` accepts only fixed sanitized TRANSIENT_FAILURE (retryable) or INTERVENTION_REQUIRED (blocked) diagnostics. It appends one immutable ATTEMPT_DIAGNOSTIC/attempt/RESULT row, clears the lease, increments rowVersion and returns the new rowVersion. There are no scores/bands or frozen INPUT/MANIFEST writes. Unknown database/constraint failures remain sanitized WORK_PERSISTENCE_UNAVAILABLE, not an invented allocation conflict.

Each operation owns a REQUIRES_NEW, READ_COMMITTED transaction: lock, read authoritative clock, validate, write, verify readback, commit. **Lease clock authority is Oracle SYSTIMESTAMP**, read on the bound connection after the lock through injectable `OracleLeaseClock`; tests can inject a fixed/mutable Java Clock. Acceptance createdAt retains its existing application UTC clock. If Oracle time precedes createdAt, work fails closed. Every worker mutation checks state, token, epoch, attempt, rowVersion and exact expiry, requiring `now < expiresAt`; its conditional UPDATE checks the entire stored fence and Oracle expiry again. Failure recording inserts its diagnostic before the final guarded parent update, so expiry or failure rolls both changes back. Counters/timestamps cannot wrap; renewal never shortens expiry if the clock moves backward. Callers must use the newly returned fence after renewal. Tokens are capabilities, omitted from `toString`; never log or share them.

These operations perform no external calls under locks. Mocked transaction tests establish Spring commit/rollback paths and conditional SQL, distinct from live Oracle verification.
