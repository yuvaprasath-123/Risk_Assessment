## Opt-in service submission (risk-submission-v1)

`POST /internal/v1/risk-assessments` and `GET /internal/v1/risk-assessment-submissions/status?submissionSource=...&submissionKey=...` require the separate **RISK_ASSESSMENT_SUBMIT** service permission. Existing manager/read permissions grant neither route. End-user JWTs remain invalid service credentials. The receiver must grant the permission and independently bind each namespace to exactly one service identity; there are no default owners or submission grants. Status lookup enforces the same namespace ownership as POST and does not claim work.

Strict JSON request (illustrative references, not existing Developer 1 endpoint contracts):

```json
{
  "contractVersion": "risk-submission-v1",
  "submissionSource": "developer1.payment.v1",
  "submissionKey": "stable-opaque-submission-id",
  "paymentReference": "123",
  "validationReference": "immutable-validation-record-reference",
  "validationRevision": "immutable-revision",
  "configurationVersionId": null
}
```

All references are strings; payment/configuration IDs are positive canonical Java Long strings. Identity is the namespaced key, **not** paymentReference. Validation revision and explicit configuration choice are optional/null. An omitted revision is allowed only when the adapter can guarantee the validation reference itself is immutable. Unknown/duplicate fields, coercions, unsupported versions and invalid bounds are rejected; bodies over 16,384 decoded characters are rejected. Request facts, PASS flags, scores, hashes and evaluator versions cannot be supplied. The authoritative facts adapter must verify PASS, payment/submission ownership, immutable validation reference/revision and all engine facts/excluded retry aliases before acceptance. Exact duplicates remain Developer 1 validation's responsibility. Stable retry identity versus genuine linked resubmission still needs Developer 1 confirmation.

POST returns **200** for a verified stored COMPLETED result, otherwise **202** with status and `result: null`. The JSON fields are `assessmentId`, `rowVersion`, `status`, `cutoff`, `configurationVersionId`, `configurationRowVersion`, `completedAt`, `result`, `retryAllowed`. IDs/revisions are strings, times UTC, scores exact integers. COMPLETED `result` uses the existing safe `{rawScore, finalScore, maxFinalScore, band}` projection. BLOCKED has `retryAllowed: false`; other non-completed states permit caller retry and POST sends `Retry-After: 2` seconds as polling guidance, not lease expiry. GET status is 200 with the same body, including non-completed states; no writes/evaluation/dependency calls. Both responses use `Cache-Control: no-store`. The caller uses the same identity after an uncertain response; never generate a new key just to retry. No leases, diagnostic text, accepted facts or raw evidence are returned.

Errors are sanitized using the existing error envelope: 400 INVALID_SUBMISSION, 403 SOURCE_FORBIDDEN, 404 SUBMISSION_NOT_FOUND (lookup), 409 SUBMISSION_CONFLICT, 503 SUBMISSION_DISABLED / ADAPTER_UNAVAILABLE / DEPENDENCY_UNAVAILABLE / SUBMISSION_UNAVAILABLE. Existing authentication returns 401/403. A pre-acceptance dependency failure returns 503 and creates no assessment; the caller can retry the same identity. Once accepted, dependency failures are recorded as RETRYABLE_FAILURE without score/band and returned as 202. An uncertain database outcome may return 503; always use lookup before deciding what to retry.

Execution is one synchronous attempt: existing acceptance -> fenced claim -> complete evidence bundle freeze -> pinned finalization. Every existing persistence phase keeps its own short transaction; external adapter calls and pure engine evaluation run outside transactions. Claim conflicts return the current status; they do not launch another worker. No queue, scheduler, Kafka, callback or background persistence is introduced. Dependency reads share an explicit positive budget up to 30 seconds, a two-thread zero-queue executor, cancellation and a propagated monotonic deadline; adapters must implement finite transport timeouts and read-only operations. Uncooperative timed-out dependencies occupy bounded capacity and later calls fail closed. New orchestration JDBC templates use five-second statement timeouts; fresh evidence is limited to 10,000 aggregate records. There is no single hard wall-clock HTTP deadline covering every JDBC statement and CPU phase: driver cancellation and transport limits must be verified live. An expired lease cannot authorize freeze/completion; retry may reclaim expired work.

Completed retries verify and return stored results without rescoring, resolving active configuration, or fetching facts/history. Other retries compare payment/validation references and any explicit version with the original accepted record, restore its exact facts/configuration/cutoff, and reuse frozen evidence if present. Omitted configuration always means reuse for an existing identity, never latest active. A concurrent first acceptance follows the unique winner and rechecks all verified facts with its cutoff; differing facts still conflict. Immutable validation reference/revision is therefore a mandatory upstream guarantee, not an assumption that mutable records will stay unchanged.

Before evidence exists, the adapter must reproduce the **original** cutoff, coverage, eligible supplier-wide records, current/retry exclusions and source references. Unavailable/incomplete required evidence never becomes empty authoritative history; freeze rolls back and work remains recoverable. If the source explicitly cannot reconstruct that cutoff, it raises CUTOFF_NOT_REPRODUCIBLE: orchestration records BLOCKED with a fixed sanitized intervention diagnostic. This milestone provides no unblock or lineage-replacement API. Agreement on recovery/retention or an externally confirmed new resubmission is required; advancing cutoff or replacing accepted facts is forbidden. Frozen evidence survives failure/takeover and is locally verified before reuse.

## Evidence adapter contract

`EvidenceAdapter` is an integration port only. Adapters must provide same-supplier INR evidence, an exact common UTC cutoff, stable source snapshot IDs, sufficient coverage and an explicit COMPLETE/UNAVAILABLE/INCOMPLETE status. COMPLETE is an authoritative completeness guarantee, including pagination and as-of status, not merely a successful API response. Payment windows are `[cutoff-windowSeconds, cutoff)`; amount baselines use completedAt, activity/near-duplicate histories use submittedAt. Supplier creation/reactivation age windows include both endpoints. New-supplier evaluation needs exactly one supplier snapshot; reactivation also needs actual status transitions. PriorAssessment represents a completed assessment's original triggered factors; overrides do not erase that original evidence.

For unavailable dependencies, `Evidence.unavailable(supplierId, currencyCode, cutoff)` records the requested scope without inventing a source snapshot or coverage. Those metadata fields are mandatory for COMPLETE evidence; unavailable/incomplete evidence always fails enabled dependent rules.

The engine excludes supplied current/retry submission identities before evaluating history and deduplicates identical historical rows by logical submission identity. Conflicting rows fail closed. Previous flags count distinct submissions, and PREVIOUS_RISK_FLAGS cannot qualify itself. No assessment-once enforcement is claimed. Adapters must agree submission/resubmission identity, canonicalize retry records, certify historical validation and resolve Developer 1 LocalDateTime values to the agreed timezone. Current requester-scoped payment APIs cannot supply authoritative history across requesters. Payment/invoice DTOs lack currency; previous factor history and validation handoff APIs are not available. No endpoint is assumed to exist.

## Scoring finalization library contract

`RiskFinalizationService.finalizeAssessment(FinalizationRequest)` takes the namespaced identity, current post-freeze/renewal `WorkLease`, and expected acceptance/configuration/input hashes. Hashes are preconditions: persisted configuration, acceptance and the complete frozen graph are independently reconstructed and verified locally. No supplied score, factor or replacement input is accepted. The pinned executable registry currently supports **`risk-scoring-v1`** only; accept this evaluator identity for new work. Unknown historical identities fail closed with `EVALUATOR_UNAVAILABLE`; they are never silently aliased to the current engine. Retain executable versions and canonical decoders for historical work.

Execution has three phases: a short Oracle `SET TRANSACTION READ ONLY` snapshot; pure evaluation with any caller transaction suspended and no database lock; then a REQUIRES_NEW writable transaction locking the parent and verifying the frozen identity/graph plus the full lease again. ## Work claiming and fencing contract

`RiskEvidenceService.freeze(EvidenceFreezeRequest)` accepts a current `WorkLease`, the explicit original `AcceptanceRequest` with typed configuration, a supplied immutable `RiskInput`, and four `Kind -> Source(service, recordReference, revision)` dependency provenance entries. Historical payments/prior assessments must already exclude current/retry identities. Prior assessedAt remains the adapter's original COMPLETED_AT contract. COMPLETE includes an upstream completeness/as-of guarantee; this operation cannot independently verify pagination or historical visibility.

Partial capture is **all-or-nothing**: required UNAVAILABLE/INCOMPLETE/short coverage rejects with EVIDENCE_NOT_READY and no input writes. A successful freeze appends five INPUT rows (CURRENT_INPUT, PAYMENT_HISTORY, SUPPLIER, SUPPLIER_TRANSITIONS, PRIOR_ASSESSMENTS), all attempt 0, and one MANIFEST/ENGINE_INPUT row referencing their IDs/hashes and the full canonical input. `risk-evidence-canonical-v1` uses exact scale-two money strings, UTC nanoseconds, explicit nulls, sorted object keys/declared sets, and preserved record-array order.
